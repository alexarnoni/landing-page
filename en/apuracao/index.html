Live Election Count

I track the 2026 presidential runoff count in near real time, project the final result with an uncertainty band, and keep in plain sight how much the projection missed. A day after the runoff I started a similar dashboard for the US midterms.

Open the site View on GitHub

Problem

During a count, the partial tally misleads: ballot boxes arrive in uneven order, by region and by city size. On 25 Oct 2026, with 42% of ballot boxes counted, the raw count showed 49.83% for Lula, and the final TSE result was 51.79%.

The project answers two questions: how to follow the night with official data refreshed every 20 seconds, and how to estimate the final result while being honest about how wrong the estimate can be.

Data

Results come from the TSE's public publication files (tracking and per-election results), and state and city outlines come from IBGE. The projection compares against the first round, by municipality. The project is unofficial and has no link to the TSE.

To test ideas without waiting for the next election, the repository has experiments over 499 thousand polling sections (votes per section, ballot-box arrival time and ballot-box bulletins), all described in docs/.

Technical decisions and trade-offs

  • Visitors never call the TSE. A poller reads the tracking file every 20 seconds and only downloads results when the tally timestamp changes, with ETag, growing back-off on errors and detection of stale CDN data.
  • Only the TSE declares a winner. The site shows the elected candidate only when the file indicates final tally and the TSE itself flags the candidate. Projection and "mathematically decided" are the site's own calculations and are always labelled as such.
  • Layered swing projection. It compares each counted municipality with its first-round vote, measures the vote shift by region and state, and applies it to what is still missing, with a 95% band. The model version and parameters are recorded in every output.
  • What went wrong is recorded too. docs/hipoteses.md lists each hypothesis, the test and the decision, including the discarded ones. One that was adopted: weighting the swing by votes cut the mean absolute error from 0.210 to 0.079 percentage points in a backtest using the real arrival order of municipalities, and the gain held or tied at every stage of 200 simulated nights.
  • A closed edition becomes a static site. An exporter builds the frozen copy from the night's archive, and hosting (Cloudflare Pages) publishes only that branch, with no server running.
  • The midterms dashboard needed more care with its source. It reads civicAPI through a Cloudflare Pages Function. On the night of 3 Nov the source took 15 to 60 seconds per request and returned 503 errors. The fix was one independent request per chamber (House, Senate, governors), a copy of each chamber's last good page, a deadline and a request cap (the free plan cuts off at 50) and, with the source down, the last valid data with an on-screen warning.

Result

On 25 Oct 2026, the projection that ran that night (version swing-1.0) missed by 0.10 percentage points on average. The table compares its error with the raw count's at three moments:

The code has 146 unit and integration tests and 21 browser tests that run in Chrome. The 2026 edition is live as a frozen copy. The project is configured by an election profile (config/perfil.json), so 2028 and 2030 need little change.

The US dashboard started on 26 Oct and was refined until election night, 3 Nov. On 6 Nov 2026 it showed 412 of 435 House races projected (251 Democrats and 161 Republicans), from civicAPI.

Limitations

  • The projection was calibrated on a single election. That night's 95% band covered the final result at only 38% of moments: it was too narrow, mostly near the end. The current model (swing-2.0) widens the band and uses a different weight in the average, but it has only been validated on simulated nights.
  • The swing's unit is the municipality. It does not correct the bias of ballot boxes that arrive first within a single city.
  • Signature validation of the TSE files is not implemented.
  • The US dashboard depends on a free, unstable API. Winner projections there come from the source and are not official results, and at the end the source stalled with 23 House races unprojected.
  • The idea of comparing each counted part with the previous election and estimating the shift by layers (country, region, state) comes from the method Rodrigo Mahlmeister published during the 2026 count. The code is mine.
